## 2026-06-17 Review Intent Idempotency Scope

- `review_intent` idempotency is scoped to `delivery_id`, `kind`, `repository_id`, and `pr_number`.
- GitHub can send one delivery that references more than one pull request for check events. Even though the initial durable contract only enqueues pull request lifecycle events, the database constraint should preserve pull request scope so future check-driven review intents cannot suppress sibling pull requests.
- The webhook deferred-claim filter is intentionally limited to lifecycle events that write a durable `review_intent`: `opened`, `reopened`, `ready_for_review`, `synchronize`, and `closed`. Broader review/comment/check events should only move to deferred claiming when they also persist an explicit intent kind.

## 2026-08-31 Production Deployment Topology

Tribunal deliberately runs the proxy, engine, and web applications as singletons. The production workflow deploys each application and immediately runs `flyctl scale count 1 --yes --app tribunal-<service>`; `.github/tests/production-migration-gate.test.ts` treats that exact command as a load-bearing constraint and fails if it is removed or separated from its corresponding deploy step.

Scaling any application above one Machine requires revisiting the affected contracts before rollout:

- The web application's per-user MCP handler cache and `subscriptions/listen` delivery do not provide cross-replica fan-out. A stream is reachable only from the Machine holding it.
- Redis-backed rate limiting, concurrency caps, and failed-authentication lockout remain correct shared-state mechanisms, but Tribunal does not claim they have been exercised against more than one live replica.
- MCP metrics are per-instance metrics for the sole web Machine. A multi-replica deployment requires an aggregation contract.

This constraint does not replace the engine's independent singleton lease. The engine lease prevents concurrent workflow ownership even if deployment topology drifts; the production scale command keeps the intended topology explicit for all three applications.

## 2026-09-11 Redis Client Reconciliation

Tribunal runs one Redis client per process. The web process shares the single client that `packages/github/src/cache.ts` `createCache` already owns between GitHub API response caching and the MCP rate-limiter / concurrency-cap stores (TRI-49), rather than opening a second connection. The proxy and engine processes each call `createCache` and keep their own client; only the web process hosts the MCP limiter, so web is the only place the client is shared.

- The two consumers use disjoint keyspaces — `github-*` cache keys versus the limiter's `tribunal-mcp:*` keys — so one connection introduces no correctness or `cachedRead`-bypass risk. `cachedRead` is client-agnostic (it calls the injected `getCached`/`setCache`), and the limiter uses different commands (`eval`, `zRem`, sorted sets) on different keys.
- The library's store factories accept a structural `{ eval, zRem }` client (`MinimalRedisClient`), which the node-redis client satisfies. Sharing therefore needs only an accessor, no adapter and no second `redis` dependency (it stays a single dependency of `packages/github`).
- The accessor `createCache(...).getRateLimitClient()` returns the shared client narrowed to `Pick<RedisClientType, 'eval' | 'zRem'>`. The narrowing is intent-signaling and connection-safety, not an ironclad bypass guard: it keeps `.get`/`.set` off the accessor (so GitHub responses are not _accidentally_ cached around `cachedRead` through it) and, more importantly for a shared connection, keeps `subscribe`/blocking commands off (those would break the connection the cache also uses). It is not airtight — `eval` runs arbitrary Lua and a cast can widen the type — so the real "no path around `cachedRead`" guard remains that contract and its lint rule (`.claude/rules/github-api.md`), unchanged here.
- Two clients were rejected: a Redis _server_ outage — the dominant failure — hits two connections exactly as it hits one, so a second client isolates only rare per-connection faults, at the cost of a second connection and a second reconnect policy. In a singleton deployment that is not worth it. Failure _policy_ stays per-consumer on the one client: GitHub caching fails open (unchanged); the MCP limiter (TRI-56) owns its own behavior when the client is down.
- Reconnect is bounded (TRI-49 AC3): `createClient` is given `socket.connectTimeout` and a `reconnectStrategy` that returns an `Error` after `MAX_RECONNECT_ATTEMPTS`, so `connect()` against an unreachable Redis fails fast instead of hanging startup. The lazy client reuses its connection only while `isOpen`, so a client whose reconnect gave up is recreated on the next call rather than returning a permanently-closed client. Whether a _runtime_ outage that exceeds the cap is recovered by process restart is out of scope here and belongs to TRI-51 (process lifecycle); the `isOpen` recreation covers recovery on the next call in-process.
- `REDIS_URL` remains optional in the web environment schema so local development without Redis still works (the criterion's `isRedisConfigured()` never existed in this repo). The property it actually protects: dev without Redis works because the MCP limiter stays in-memory and the GitHub cache degrades. It is `optionalUrl` (blank `REDIS_URL=` normalizes to undefined, not a `.url()` failure at startup), and registering it in the schema and `turbo.json` `globalPassThroughEnv` closes a pre-existing gap and lets TRI-56 add its production "refuse to boot without Redis" refinement as a one-line `superRefine`.
- The cache's fail-open, precisely: it lived in `cachedRead`, which catches a failed read and falls back to GitHub — not in the cache operations themselves, which awaited `getRedisClient()` outside their `try`. The direct-usage exceptions (`installations/access.ts`, `core/rate-limits.ts`) that bypass `cachedRead` were therefore only ever protected by node-redis's _hang_ on an unreachable Redis; the bounded reconnect turned that hang into a fast rejection, which would have surfaced as a thrown exception on the repository-authorization path. So the fail-open now lives in the operations too: `getCached`/`setCache`/`setCacheIndefinitely`/`deleteCache`/`deleteCacheByPattern` translate a _connection_ failure to `null`/`false`/`0`. A missing `REDIS_URL` stays loud (`RedisNotConfiguredError`, rethrown) because that is misconfiguration, not an outage; `getRateLimitClient()` also stays rejecting, so the limiter (TRI-56) can fall back to in-memory rather than silently losing admission control.
- Fail-fast cost, stated (not hidden): with `MAX_RECONNECT_ATTEMPTS = 3` and `connectTimeout = 3000ms`, an _unreachable_ Redis (SYN blackholed, not refused) takes ~12s for `connect()` to reject; a refused connection is ~300ms. The failure is not memoized — `client` is only assigned after a successful `connect()` — so every cache/limiter call during a sustained outage re-pays that budget before failing open, and the pre-existing near-simultaneous-first-caller race (each caller builds its own client because `client` is set only after `await connect()`) means N concurrent callers each burn it. This is strictly better than node-redis's prior infinite hang and is acceptable for the GitHub cache (fails open, degraded). A negative-cache marker or connect coalescing to bound repeated-outage cost is a possible follow-up for the limiter's hot path (TRI-56) or process lifecycle (TRI-51), not done here.
- Forward note for TRI-56: consume `getRateLimitClient()` per operation (or re-acquire on `ClientClosedError`) rather than caching the returned object in a module-level variable. After a reconnect-exhaustion event the accessor rebuilds the client, but a cached reference would stay pointed at the dead one, since nothing else invalidates it.
