# GitHub Cache Identity Audit

Issue: #204
Date: 2026-07-25

## Verdict

A cache coalescing defect was found and fixed: pull request detail reads and pull request metadata reads previously shared the same cache key even though they store incompatible payload shapes. Follow-up issue: #232.

No missing user, installation, repository, pull request, issue, branch, or commit identity dimension was found, and no cross-user cache leak was found. The cache entries that intentionally do not include a user identity are repository, pull request, installation, branch, commit, or global GitHub App reads where the returned data is not viewer-specific after the caller has already established authorization.

> [!IMPORTANT] Superseded in part, 2026-09-02
> That second paragraph was wrong about the _installation_ dimension, and the
> error is instructive: it reasoned that a repository read is safe to share
> once "the caller has already established authorization." Authorization
> establishes that a caller may read _a_ repository; it does not establish
> _which installation's view_ of it they are entitled to. A repository that
> carries `github_installation_repository` link rows for two installations —
> the state a transfer leaves behind — has two different private views behind
> one repository identity, and `cachedRead` answers a hit without invoking the
> Octokit client, so the credential that would have distinguished them is
> never used.
>
> TRI-108 partitioned `get-pull-request`, `get-pull-request-metadata`, and
> `list-pull-requests` by installation; TRI-110 did the same for
> `list-issues`. The rows below reflect the current keys.
>
> Still open: `get-pull-request-diff-context` keys on
> `(repositoryId, pullNumber, headSha)` with no installation segment, and the
> web routes select an installation with
> `resolveInstallationForRepository`, which returns the most recently added
> active link rather than the installation the caller was authorized through —
> so those routes can hand a caller another installation's Octokit even on a
> cache miss. Tracked separately; do not read the table below as clearing
> either.

## Cache Bypasses

| Bypass                                                                                           | Reason                                                                                                               | Verdict            |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `listPullRequests` without `repositoryId`                                                        | No stable stored repository identity is available for the cache key. Production dashboard calls pass `repositoryId`. | Acceptable bypass. |
| `listIssues` without `repositoryId`                                                              | No stable stored repository identity is available for the cache key.                                                 | Acceptable bypass. |
| `getDiffContext` without `repositoryId`, without `headSha`, or when `currentHeadSha !== headSha` | Diff context must match the reviewed current head; stale head data would be wrong.                                   | Acceptable bypass. |
| `mintSingleRepositoryReadToken` after cached token decryption fails                              | Deletes the bad key and refreshes the same `installationId` + `repositoryId` identity.                               | Acceptable bypass. |
| `getDefaultBranchCiStatus` when cached `commitSha` or `requiredKey` mismatches                   | Branch cache key is branch-shaped, so payload validation prevents cross-commit or cross-required-check reuse.        | Acceptable bypass. |
| GitHub OAuth callback `listUserInstallations(..., { bypass: true })`                             | Write-then-read after App install flow; stale user installation list could reject newly granted access.              | Acceptable bypass. |
| Webhook subscription confirmation paths `getRegisteredWebhooks(..., { bypass: true })`           | Operator confirmation must not report stale subscription drift for up to the 24-hour app-configuration TTL.          | Acceptable bypass. |

## Bypass and Direct Cache Usage Audit

Direct `getCached` / `setCache` use outside `cachedRead` is limited to non-GitHub-resource caches or intentionally specialized caches:

- `packages/github/src/installations/access.ts` caches user repository access under `userId` + `repositoryId`.
- `packages/github/src/core/rate-limits.ts` tracks installation rate-limit state under `installationId`.
- `applications/web/src/lib/server/github/access.ts` is still imported by web auth/account paths for cache invalidation and token invalidation; its access key shape is also `userId` + `repositoryId`.
- `applications/web/src/routes/health/+server.ts` writes a global Redis health key containing only `ok`.

No inline `getCached` / `setCache` call was found caching a GitHub API read under a broader identity than the underlying data.

## Regression Coverage

`packages/github/src/core/cache-policy.test.ts` now includes an identity-coalescing regression table that varies every required key argument independently for the registered GitHub resource policies. `packages/github/src/reviews/diff-context.test.ts` verifies pull request metadata reads use `GITHUB_PR_METADATA` and cannot consume a transformed `GITHUB_PR_DETAIL` cache entry.
