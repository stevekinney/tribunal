# Learnings from the MCP dependency-model review cycle

Recorded per `AGENTS.md`: when compiling review feedback, record learnings in `documentation/learnings/` and update relevant rules. Sources are the review cycles on [#325](https://github.com/stevekinney/tribunal/pull/325) (adopting the published MCP engine) and [#326](https://github.com/stevekinney/tribunal/pull/326) (splitting TRI-37, settling the disabled-surface status). Fifteen rounds between them, and most findings after the first few were self-inflicted — which is itself the most useful thing here.

## Cross-repository graphs and release gates

- **A dependency stated in prose is not a dependency.** This graph produced the same defect five times — TRI-78→TRI-80, TRI-80→TRI-29, TRI-29→TRI-30, TRI-83→{TRI-43, TRI-52, TRI-56}, TRI-69→TRI-40 — and in every case the issue body already described the dependency in a sentence. A body paragraph is only read after someone has picked the issue up, which is too late to stop them picking it up. Use the native `blocked by` relation.
- **Detection is not ownership.** Verifying at the consuming end that an artifact has the capability you need is a safeguard against adopting the wrong thing; it is not a plan for producing the right thing. TRI-80 verifies registry injection against the installed package, which correctly refuses a premature version — and on its own converts a silent wrong-version adoption into a permanent stall, because no release issue owned publishing the corrected build. Every "refuse if wrong" needs a matching "and here is who makes it right."
- **Two individually reasonable completion rules can combine into a deadlock.** "Publish early for pipeline shakeout is allowed" and "an upstream issue is Done when its pull request merges" are both defensible. Together they let every blocker on a downstream adoption issue clear while the registry still holds an unusable build. Check what a set of completion semantics permits jointly, not one at a time.
- **State a completion bar as a rule, not a list.** The publish bar here was first written as "capability-complete", meaning two named issues, which silently excluded a third carrying the identical requirement. Enumerating invites that omission every time the set grows. "Every upstream change the adoption issue's criteria require" covers issues filed after the sentence was written.
- **`Ready` on an upstream blocker needs a released version, not a merged pull request** — and not merely any released version, but one that contains the specific change. Merging upstream moves nothing downstream.

## Feature flags and disabled surfaces

- **Choosing a status code is necessary for indistinguishability and does not deliver it.** `404` is the only status that can make a flag-disabled route look unmounted, because an unmounted SvelteKit route already returns it. But a short-circuiting handle returning `404` can still emit a distinctive body or an extra header, and a prober reading those learns exactly what the status was chosen to hide. If indistinguishability is the security goal, assert the whole response, not the status line.
- **`503` invites a retry that should never happen.** RFC 9110 defines it as _temporarily_ unable and pairs it with `Retry-After`. A surface disabled on purpose is not temporarily unavailable in any sense a client should wait out, so `503` has every client politely retrying it. For OAuth discovery specifically, `404` is also how a client is _supposed_ to learn a host does not offer the surface, and degrade.
- **A response header only governs responses issued from its own deploy onward.** `Cache-Control: no-store` on a disabled route does nothing about entries a cache already holds from before that deploy — and a `404` is heuristically cacheable under RFC 9111. For unauthenticated `GET`s like OAuth discovery documents, a pre-existing negative cache entry can keep hiding the surface after it is enabled. Third-party caches cannot be purged, so ship the header with the mount rather than at enable time, which bounds the window, and name the stale entry as an expected failure hypothesis at enable rather than debugging it as a mystery.
- **A safety rule that forbids the work it protects gets routed around.** "Do not enable this flag in any environment" blocked the very issue that had to verify the enabled state. The failure mode is not that the work stalls — it is that an implementer ignores the instruction because it is obviously wrong for their task, and then the rule protects nothing while still reading as protection. Scope prohibitions to where the risk actually is: production and publicly reachable deployments, not local and CI.

## Assigning work in decision documents

- **A question deferred to an owner that does not exist is not deferred, it is dropped.** Three instances here: a conformance-fixture decision assigned to "whichever issue ports `conformance-server.ts`" when the dependency model left no issue doing that port; a consent-screen UX decision assigned to an issue that was already Done and had explicitly scoped itself away from it; and a scope-default revisit whose only named owners were terminal release gates that merely _observe_ client behaviour and could all complete without acting on what they found.
- **Do not assign an issue a criterion it cannot verify.** Recording an expected value for behaviour that does not exist yet is paperwork that reads as coverage — this codebase's signature defect wearing a checklist. Give the disabled-state assertions to the issue that builds the disabled state, and the enabled-state assertions to whichever issue can produce an enabled surface.
- **Approved does not mean nothing inside is open.** A decision document can be approved with named items deliberately handed onward. Flipping its status while deleting those items launders unresolved work into apparent completion; strike them through and record who owns them instead.
- **An approval record answers the question it was asked, not adjacent ones.** Three decision documents here were approved without recording answers to sub-questions inside them. The resolution is to give each sub-question a named owner, never to invent the answer to tidy the record.

## Reviewing your own documentation changes

- **Sweep for the concept, not for your own phrasing.** The most persistent defect across these two pull requests was correcting a claim in one place while an older statement of the same fact sat elsewhere. Grepping the wording you just wrote only finds the sites you already knew about — the sentence that mattered read "Checks 1, 2, and 4 belong to whichever issue implements the flag" and shared no phrase with the search that had come back clean. Search for the subject.
- **Sweep across documents, not within one.** A fixed attribution in the orchestration document left the same invariant misattributed in the scope document, which quoted it verbatim.
- **Sweep into the tracker.** Twice, a corrected document disagreed with a Linear issue body that carried the same assignment. Where they can disagree, say which one wins.
- **Adding precision creates new contradiction surface.** Every round that made ownership more specific generated the next round's finding, because a precise claim can conflict with a vague one that previously read as compatible. Expect it, and re-check the whole class after each pass rather than only the line that was flagged.
